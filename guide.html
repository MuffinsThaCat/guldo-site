Guide

The challenge compiler

How to describe a problem, turn it into a fair test, and check a certificate, including what each step can't do. This page is generated from COMPILER.md in the repository, so it matches the code. It is the technical reference: the later sections (counted rounds, the restricted subset, derived claims) assume you know the basics, and the plain-words version is on Other claims. How each claim was tested, round by round, is on the Audit history page.

If you read only this

  1. You write three small pieces: make a test question from a secret number, check an answer exactly, and a plain baseline solver.
  2. compile_domain.py check NAME takes seconds and tells you what to fix. compile NAME --quick gives a draft in minutes. compile NAME is the real one and can take hours.
  3. A certificate lets anyone recompute a result, but only shows the costs were honestly measured if the verified sandbox (the “locked box” elsewhere on this site) or a re-run backs it. Checking one never runs its code unless you pass --execute.
  4. Past speedups: a cost can be an exact instruction count that anyone reproduces, and a certificate can back a benchmark score or a verified negative result. These are newer and have never been run: see Other claims.

Practice stage. A certificate can show the arithmetic adds up, but not that the CPU costs were honestly measured. Nothing is certified as official until a full round has been evaluated in the strict test environment (the locked box) on a dedicated machine.

You declare a problem. The compiler turns the declaration into a verified, calibrated challenge: an instance family with a size ladder, a CPU cap and an instance count chosen from measurements, a power analysis saying which speedups it can and cannot certify, a self-tested pipeline, a server plan, and, afterwards, a certificate anyone can check.

Everything downstream of the declaration is the protocol that already exists (commit-reveal seeds, the difficulty-stratified lower bound, the hash-chained log, the sandbox). The compiler writes no new trust rules; it automates the part that used to take a week of hand calibration per domain (PROTOCOL.md, "Power at the official configuration"), and it refuses to emit a challenge it cannot validate.

Quick start

python3 compile_domain.py init mything              # a WORKING example in domains/mything/ (it already passes check); never overwrites
# ... edit the lines marked EDIT: derive(), verify(), DOC, SIZE_RANGE, and the reference solver ...
python3 compile_domain.py check mything             # seconds: what is wrong, and how to fix it (shape, determinism, anti-cheat, reference)
python3 compile_domain.py compile mything --quick   # 1-2 minute DRAFT ladder, for iterating (practice only)
python3 compile_domain.py compile mything           # the real compile + self-test: tens of minutes to hours; prints READY / NOT READY
python3 compile_domain.py show mything              # that verdict again, with the exact next commands
python3 compile_domain.py recheck mything           # seconds: recompute every checkable claim in the compiled record and compare (see "Checking a compile")
python3 compile_domain.py status                    # every declaration: registered, self-tested, or stale (and why)
python3 submit_check.py my_solver.py --family mything

Every command takes the NAME or a path (domains/mything). compile_domain.py --help prints this workflow. init --blank gives an empty skeleton instead of the working example.

A compiled domain is a family like gm, mlwe and factor: judge.py, official.py, ops.py, the portal and the site all accept --family mything. domains/dlog/ is a worked example the compiler was not written for (discrete logarithm by exhaustive search).

The declaration (domains/<name>/decl.py)

namemeaning
NAME2-16 lowercase letters, equal to the directory name (ladder files are recognised by that pattern)
VERSIONany string; bump it whenever derive() changes (it is recorded in every results file and refuses to compare across versions)
SIZE_RANGE, SIZE_STEPthe sizes the compiler may use; it finds the ladder inside this range
REFERENCE_SOLVERa file inside the directory with a top-level solve; every submission is measured against it
derive(master, size, idx)a pure function of its arguments returning {"args": [...JSON...], "planted": <a valid answer>}
verify(inst, ans)exact check; must reject everything that is not a real answer
witness(inst)optional: the answer to feed verify when planted is not itself an answer
DOC, SIGNATUREoptional text for the Compete page and the challenge document
REFERENCE_NOTEone or two sentences: what the reference algorithm is and what is known to beat it. Strongly advised: check warns without it, and the challenge document, the domain card and the compiled record say "not stated"

The solver is called as solve(*args) and returns an int, a list of ints, or None (the runner's contract, unchanged).

decl.py is operator code. It runs in the judge's process exactly like instances.py does. Submissions never see it: they run in the sandbox with only runner.py and their own file. Do not compile a declaration you did not read.

The passes

  1. parse. The declaration has the required names; NAME is not a built-in; the reference lints clean (an import the sandbox image lacks is a FAIL, because the baseline is measured there) and imports none of the judge's modules.
  2. validate. Each is a PASS / WARN / FAIL with the reason, and any FAIL stops the compile and writes nothing:
    • shape: args is a JSON-serializable list and under 1 MiB (it crosses a process boundary);
    • determinism: the same (master, size, idx) gives the same instance; different indices and different seeds give different ones (an instance that ignores the seed would make the commitment commit to nothing);
    • process purity: the same instances come out of fresh interpreters under two different PYTHONHASHSEEDs (catches hash-order, clock and global-random dependence, which would make another machine derive different instances);
    • witness: verify accepts the planted witness at three sizes, and the witness (or a large part of it) is not in the arguments;
    • junk rejected: verify rejects 19 junk answers (None, 0, 1, -1, strings, empty lists, ...). A verifier that accepts 1 has an answer space a solver can guess;
    • no trivial answer: no argument, neighbour of an argument, or the argument list verifies, so the answer is not read off the question;
    • witness reuse: one instance's witness is not accepted by other instances (otherwise a stored table of past answers would solve every new challenge; EGG.md in the repository describes how that happened to an earlier design);
    • reference solves: the reference solves the smallest instances with an answer verify accepts, deterministically.
  3. profile. The reference is run, locally, on a public profiling seed (never a competition seed) at growing sizes until its cost passes a third of the probe budget: a calibration profile of median cost, per-instance spread (sd of log2 cost) and timeout rate.
  4. optimize. From the profile: the CPU cap (30, 60, 120 or 240 s, the smallest that gives a usable ladder), and 3-6 sizes whose predicted median costs run from 2 s up to a point where about 10% of instances time out, spanning at least three octaves (the estimator's difficulty bins are octaves of baseline cost above 0.5 s). The chosen sizes are then measured (8 instances each) and the ladder is re-chosen if a prediction was off by more than an octave.
  5. power. The real estimator (extrapolate.measured_by_difficulty, through power.synth_trial) on synthetic ladders drawn from the profile, with a synthetic submission that is exactly e bits faster. The compiler picks the smallest instances-per-size n (12, 24, 48, 96 or 192) for which all three seeds are credited at >= 1 bit with probability >= 80% at a 2-bit true speedup, then tabulates power by speedup. Output: the range of speedups the challenge can certify and the zero-effect false-credit rate.
  6. emit. compiled.json, plus out/CHALLENGE.md (local kit), out/server_plan.json (the ops.py commands and CPU-hours), out/ci_check.sh and a CI workflow template, out/CERTIFICATE.md.
  7. self-test. The compiled domain is run through the real pipeline (judge.py evaluate -> harness -> extrapolate.py) on a throwaway seed in local mode, with three controls:
    • zero effect: the reference submitted against itself must earn < 1 bit;
    • failure: a solver that never answers must earn 0;
    • known effect: the same ladder with every solved cost scaled by 2^-1 must be recovered (a credit between 0.4 and 1.3 bits). If any control fails the domain's record says so, and rounds.create_round refuses an official round for it. The control ladders are kept in results/ (named control_zero and control_none, so do not give a real submission those names: the site's Results page leaves them out on purpose, as they are controls, not results).

What registers a domain, and what un-registers it

families.py calls declared.load_all() at import, so every process sees the same registry. A domain registers only if compiled.json is fresh: it records the SHA-256 of decl.py and of the reference solver, and a mismatch (any edit to either) un-registers the domain until it is compiled again. compile_domain.py status lists the reason. A round's rules fingerprint (log entry 0) includes the hashes of decl.py, compiled.json and the reference, so the declaration cannot change under a running round without the evaluator refusing, and a certificate can show which declaration its numbers came from.

Submitting and verifying from the command line

svp.py (guide: SUBMIT.md) is the user-facing path: submit a solver to a round, status, and verify --round R --id I, which downloads the certificate described below and checks it against the server's own log and your own receipt. svp.py practice SOLVER --family F certifies a local run on your own seeds, no server needed. ops.py certs builds the certificates after the reveal.

Provable costs (counted.py, count_runner.py)

The one thing a certificate cannot prove by checking is that recorded timings are what a real run took. Step counting replaces the clock with a number anyone can reproduce exactly: the count of Python bytecode instructions a solver executes (sys.monitoring, Python 3.12+; imports, the garbage collector and the hash seed are controlled, so for a deterministic solver nothing about the machine enters the count; it still depends on the Python version and build, and a solver that depends on memory addresses, the clock or randomness counts differently between runs, which the determinism self-check refuses to certify). counted.py evaluate writes ladders in the ordinary format (cost = count / 1e6, a unit called a "counted second", plus the exact steps of every record), so the estimator, certificate.py build and the site read them unchanged. A counted certificate carries count (unit, interpreter, its own size ladder), verify adds a cost model check (every cost follows from its step count; every unsolved instance is charged the cap; every header agrees), and --rerun K --execute re-executes K instances of both solvers and demands identical counts and statuses: exact equality, no tolerance, no trust in anyone's machine, sandbox or clock. On a different Python version the re-run is a SKIP. The counting program is pinned too: every counted ladder and certificate records the hash of count_runner.py (it is not one of the protocol's hashed files), and the cost-model check fails if this checkout's differs, so counts from another counter are named as such and a later fix to the counter cannot silently change what an old certificate means (it invalidates it: re-measure with the new one). Limits, stated in the verdict: it is not a time; it cannot see work inside a C function (one instruction however long); the ladder is chosen by whoever ran it, so it is not an official round result (unless a counted round declared it, below); and it needs Python 3.12+ and pure-Python solvers. It is not wired into the compiler's calibrated challenges (those are in seconds). svp.py practice --count is the way to produce one of your own; see SUBMIT.md.

Counted rounds

ops.py round-new ... --count --count-dims 38 40 42 [--count-n 8 --count-cap 20] creates a counted round: the sizes, the instances per size, the cap, the unit, the Python version and the hash of the counting program are committed in log entry 0 (with count_runner.py and counted.py in the rules fingerprint) before any submission, so the ladder is no longer the prover's: it is the round's, the same for every participant. Source publication is forced (the proof is re-execution), and only pure-Python families are allowed (counted.family_problem: not gm or mlwe, whose baseline is fpylll). ops.py worker --unsandboxed evaluates it: no Docker, the solvers run as the operator's user under step counting, so use a throwaway user or VM; the worker refuses another Python version or counter than the round committed to (even with --accept-code-change). A solver that cheats by reading the operator's files behaves differently when anyone re-runs it, so the first re-execution exposes it. The status of a counted result is COUNTED (3 committed seeds, commitments public first, one solver and one baseline file throughout) or COUNTED, PROVISIONAL with the reasons; it is not judge.py's OFFICIAL, which means "timed in the Docker sandbox". The certificate's log check ties the counted ladder to entry 0 (a counted ladder in a round that did not declare it, or the reverse, fails), and the cost-model line then says "ROUND-DECLARED". Every record must carry a step count a re-run can reproduce (a wall-clock timeout cannot, so a certificate containing one does not verify), and the unit must equal this checkout's.

The restricted subset (what a counted solver may be). The solver runs in the SAME process as the counter, so unrestricted it could switch its own counting off (sys.monitoring.set_events(3, 0)), walk up to the runner's stack frame that holds the counter (sys._getframe, __traceback__, gi_frame), forge a result line on the real stdout and _exit, or read files: and a re-run would reproduce all of it identically, so the "proof" would pass. count_runner.py therefore enforces a restricted subset itself, before and while the solver runs (check_source, the same check rounds.submit, practice --count and svp.py submit make early):

  1. an AST whitelist: no dunder or underscore names or attributes, no frame/generator/traceback/code attributes (f_, gi_, cr_, tb_, co_), no str.format ("{0.__class__}"), no eval/exec/compile/open/getattr/setattr/vars/globals/type/object/super/id, no async code, no relative imports;
  2. a minimal __builtins__ (arithmetic, containers, print, the common exceptions) and a guarded __import__;
  3. imports only from math, itertools, heapq, bisect, functools, collections, fractions, and each import yields a PROXY exposing only named functions (a real module would leak others: fractions.sys, collections.abc.sys);
  4. sys.monitoring is removed before the solver loads, a final check fails a run whose counting was reconfigured, and, on Linux only (on macOS the limit would trip over the process's own address space), the process has a 2 GiB address-space limit;
  5. the module body is counted as well as solve() (otherwise precomputation at import time, such as a lookup table, would be free, and a solver could spin there for ever).

The rules live in count_runner.py, so the counter hash pins them: a different rule set is a different counter. The baseline must be inside the subset too (counted.family_problem). A pure-arithmetic solver needs nothing outside it (solvers/factor_trial_py.py and factor_trial_fast_py.py are inside). What it is NOT: a defence against bugs in CPython itself, against memory or time spent inside ONE C call (10**10**10: the instruction limit cannot interrupt it, the wall-clock backstop does, and that submission then fails to verify), or a replacement for running the worker as an unprivileged throwaway user (it refuses root). Source stays mandatory for counted rounds. Counting a round costs about 100x a timed run per instance: size the ladder small (the worker prints a worst case).

Derived claims (claims.py)

The machinery proves one atomic statement: program P, on inputs committed before P was seen, produced these outputs at this cost. A speedup is one reading of it. claims.py reads three others off a certificate that verifies, recomputing each from the raw per-instance records (a claim file is not trusted either: claims.py check CLAIM CERT... redoes it and demands identical output):

claims.py correctness CERT [--out F]     a benchmark score: solved/total on the committed questions (per size, per seed, Wilson 95% lower bound), for the solver AND the baseline
claims.py worst-case  CERT [--out F]     COUNTED certificates only: the largest step count seen per size, and the chance a fresh instance exceeds it (<= 1/(n+1))
claims.py negative    CERT... --threshold BITS [--out F]    "no submission in this round reached BITS": needs a certificate for EVERY submission the round's log accepted

What each does NOT show, printed with every claim: a correctness score is a rate on THIS test set within the cap (with timed costs "within the cap" depends on the measuring machine; a counted certificate makes it reproducible by anyone); the worst case is the largest value SEEN, not a bound over every input; a negative result is about the submissions made (participants chose to submit) and about what could be certified (credit is a conservative lower bound: the minimum over seeds, an inconclusive seed counts as 0), so it says "no speedup of that size was shown", not "none exists". A submission whose evaluation failed has no certificate: it is listed as missing and the negative claim is then incomplete and does not hold. The log must also contain the round's round_closed entry with no submission after it (a PREFIX of a hash-chained log still verifies, so certificates built from a truncated copy would otherwise hide later submissions), and the claim records log_head: compare it with a head hash published somewhere the operator cannot edit. The test set is the family's generator under committed seeds, so this is a benchmark of those problem families (factoring, dlog, ...), not of arbitrary data; a new benchmark is a declared domain (compile_domain.py). Tests: test_claims.py (unrun).

Certificates (certificate.py)

python3 certificate.py build  --family F --submission solvers/x.py --seed-dir S --reveal-seeds \
                              --round-data D --round-id R --out x.cert.json
python3 certificate.py verify x.cert.json [--rerun 5]

A certificate carries the claim; the rules fingerprint; the commitments and (with --reveal-seeds, which is the reveal) the seeds; both solvers' source; every raw per-instance record of every ladder; for a declared domain its three files; and the round's log. verify, on any machine with a checkout of this protocol, checks and reports each as PASS / FAIL / SKIP:

checkwhat it proves
rulesthis checkout's estimator, harness and instance code hash exactly as the certificate names
domainthe declaration, compiled ladder and reference are the hashed files, load, and are fresh
logthe hash chain verifies; entry 0 holds the commitments and the same rules fingerprint (including the domain files); the submission's hash was logged
seedseach revealed seed hashes to a commitment
sourcesthe solver sources are what every ladder header's solver_sha256 names
laddersone baseline/submission pair per committed seed (a dropped seed would raise the minimum), each on exactly the rules' size ladder with equal instance counts per size (a dropped hard size would otherwise hide failures)
coveragere-deriving every instance from the seeds gives exactly the ids in each ladder: none missing, none repeated, none foreign
creditthe credit recomputed from the raw records, with this checkout's estimator, equals the claim exactly
rerun(optional) K instances re-measured on the verifier's own machine: both solvers still solve them and the speedup reproduces within 2 bits

**A certificate is untrusted input, so verify executes nothing from it by default.** A declared domain's decl.py is hash-checked and read as data (its coverage check is then SKIPPED), and --rerun is refused. --execute imports the certificate's decl.py and, with --rerun, runs its solver sources on your machine, unsandboxed: use it only in a throwaway VM or container. Built-in families derive instances with your own checkout's code and need no flag for coverage.

verify --rerun K picks the same K instances every time unless you give --sample-seed; an independent verifier should choose its own seed so that the operator cannot know which instances will be re-measured. --tolerance BITS sets how far the re-measured speedup may differ (default 2 bits: loose on purpose, because the real machine-to-machine spread has not been measured; see "Checking a compile" for how to measure it).

Without a log a certificate can still verify but is at most PROVISIONAL (the publication time of the commitments cannot be shown); a ladder measured in local mode is PROVISIONAL regardless (only the Docker sandbox meters untrusted code). verify says which.

Checking a compile (recheck)

python3 compile_domain.py recheck dlog              # about 5 seconds
python3 compile_domain.py recheck dlog --measure 3  # also re-measure each ladder size with 3 instances on this machine

recheck recomputes what is arithmetic and compares it with the record: the declaration and reference hash as recorded; the validation checks give the recorded verdicts; the ladder, n, CPU cap and CPU-hours follow from the recorded plan; and the whole power table (seeded, so it must come out identical) is recomputed through the real estimator. Any difference is a FAIL. The arithmetic needs no trust beyond the protocol code you checked out. **But recheck is not safe on a stranger's domain:** like compile, it executes the declaration's decl.py (validation derives instances with it) and the reference solver, unsandboxed, and --measure runs the reference many more times. Read a declaration before rechecking it, or do it in a throwaway VM.

What it does not recompute: the profile's timings and the self-test, which are measurements. --measure K re-measures the ladder sizes here on the same public profiling instances (instance i is a function of the public profiling seed) and prints the gap in bits per size. A compile now records every instance's cost, so the gap compares the SAME K instances and is the machine, not which instances were drawn. A record made before that (dlog's, today) keeps only a median over all its instances, so the comparison includes sampling noise: with a per-instance spread of about 1.7 bits and K=3, noise alone gives a typical gap of 0.6 bit and one above 1.8 bits one time in ten. The output then says so and widens its warning threshold, and spread flags the recommendation as inflated. That does not prove the recorded timings; it tells you how far this machine is from the one that made them. A gap that is the same at every size is a hardware speed difference and cancels in a speedup ratio; a gap that changes with size is not. Two or more machines' --measure output is the data needed to set --tolerance honestly. None has been collected yet. To collect it: on each machine run compile_domain.py recheck NAME --measure 3 --save NAME.<machine>.json (never overwrites; it stores a hash of the host name, not the name), then merge them anywhere with compile_domain.py spread *.json. spread recommends a tolerance (the largest within-machine range of gaps across sizes, rounded up to a quarter bit, never below 1 bit because the re-measurement compares single instances whose own noise is about 0.6 bit and spread does not measure it) only when at least two distinct machines measured the same declaration; with fewer it says so and the default stays loose. The recommendation is an estimate from a few sizes, not a bound.

Attestations (attest.py)

python3 attest.py keygen --out my.key                         # a key you keep; publish the public key it prints
python3 attest.py sign x.cert.json --key my.key --out x.me.att.json --rerun 5 --execute     # verify on YOUR machine, sign the outcome
python3 attest.py check x.cert.json a1.json a2.json --trusted keys.txt

A verifier runs certificate.py verify (and optionally --rerun K, on instances drawn from the verifier's own random seed) and signs the result with an Ed25519 key: the outcome of every check, the re-measured gap, a hash of the certificate, and a self-reported machine description. check verifies the signatures and counts distinct keys.

What an attestation is worth is what its signer's identity is worth. A key proves the same party signed; it does not prove independence from the operator, because an operator can create five keys. So check reports a key as independent only if it is listed in the --trusted file you built yourself from keys you obtained out of band, and every other key is reported as "unvouched", never counted. A signed statement that the certificate does NOT verify (a dissent) makes check fail, from any key. A valid signature proves only who signed, so the statement's contents are still untrusted input: check accepts exactly the shape sign writes (a real boolean verified, short plain-text check names, a finite gap) and ignores anything else with a warning, so a hostile attestation can neither crash a caller nor count. The same goes for the measurement files spread merges, and for certificates on the site: whatever they make the verifier raise costs only that file. One key signing twice is one party. Needs the cryptography package, which the project's own venv does NOT have (install it only where you sign or check attestations). Without it, sign and keygen refuse with a message, check and the site report the attestation files as "NOT checked" and count none of them (a dissent among them would not be seen), and the signature tests in make test are skipped, not passed. Attestations do not touch the certificate, so adding one never changes its hash.

To show them on the site, put NAME.cert.json, NAME.<who>.att.json and (optionally) trusted.txt in one directory and build with python3 build_site.py --certs DIR (keep DIR outside the site's output directory: the build deletes and recreates that directory, and refuses to run if an input lives inside it). Each certificate is re-verified at build time (nothing in it executed), shown with its checks, and its attestations are counted as pinned or unvouched exactly as attest.py check does. make attest CERT=... KEY=... OUT=... is the one-command version for an outside verifier.

Exporting a challenge bundle (export_bundle.py)

python3 compile_domain.py export dlog [--out DIR] [--field "Computer Science"]     (or `python3 export_bundle.py export dlog`, `guldo export dlog`)
python3 export_bundle.py verify DIR --selftest

The compiler's output so far runs inside this project. export writes the part that ports: a directory any leaderboard can host without a copy of this repository. It refuses a stale compile (same freshness rule as emit), never overwrites, and refuses to emit a bundle that fails its OWN self-test run in a clean interpreter (python3 -I, empty working directory), so "works only inside this checkout" cannot ship.

pathwhat
challenge.jsonmanifest: problem, solver contract, ladder, protocol, power analysis, provenance, requirements, sha256 of every pinned file. status is READY or DRAFT with the reasons (compiler self-test not passed, no certifiable range, no REFERENCE_NOTE, ladder unconfirmed)
checker/decl.py, reference.py, vendor/the declaration and baseline byte-for-byte, plus any project module the declaration imports (instances.py for dlog), found by walking its imports
checker/check.pystandard library only: selftest (pinned files intact, deterministic, witness verifies, 19 junk answers rejected, reference solves), commit, derive, verify
checker/score.pyneeds numpy: score (credit vs the reference, min over seeds, inconclusive = 0), compare (is solver A really faster than B?), power
checker/estimator.pybyte copy of extrapolate.py: the scorer's numbers ARE the protocol's (a test pins them equal on the same files; on the saved dlog stride-4 ladders it reproduces the earlier claims 1.67 / 1.61 / 1.54 bits)
README.md, PROPOSAL.mdhow a board hosts it (seeds, meter, scorer run) and its limits; and the text a proposal form like Yukon's asks for (problem, verifier, link), pre-filled from the record
MANIFEST.sha256sha256sum -c-compatible; export_bundle.py verify also checks the pins in challenge.json

What the scorer adds beyond the estimator: it takes ladders in a plain JSON-lines shape ({"id", "dim", "status", "cost"}, so a board's own meter can write them), and applies the certificate's input rules to them: the two ladders must cover exactly the same instances (a truncated run is refused, not scored on the easy half), share a seed commitment (a {"meta": true, "commit": ..., "budget": ...} first line; without it the ladder is refused unless --lenient), share a CPU cap, sit on exactly the challenge's size ladder with ids exactly SIZE:0..SIZE:n-1 per size (a relabelled or duplicated-easy ladder with the right count is refused), and not reuse a seed. --lenient scores anyway and labels the result PROVISIONAL. Malformed records are refused with the line number: a solved cost must be finite and > 0 and not above the cap; a status outside solved/timeout/crash/failed/wrong is refused rather than silently charged.

The commands, in short: check.py = info, selftest, commit, derive, verify, rerun, spread, keygen, attest-check, log append|verify|checkpoint; score.py = score, compare, power, recheck. selftest, derive and verify run the bundle's own code, so they run inside the OS sandbox by default (--sandbox off to opt out).

compare answers the question a leaderboard cannot answer from ranks alone. It runs the estimator in both directions on the two solvers' own ladders (the slower one plays the baseline, so difficulty bins follow ITS cost) and says "A is faster" only when the minimum-over-seeds lower bound reaches --min-gap (0.5 bit, a convention, not a pre-registered test, but the power at that threshold is simulated and printed with every verdict). It distinguishes two reasons for no verdict. CANNOT SEPARATE means the gap is inside the noise. UNRESOLVABLE BY THIS LADDER means one solver costs under the 0.5 s floor on most instances the other finds hard, so the estimator discards exactly the evidence (the ceiling in "What this does not do"); it prints the raw median gap as description, never as a bound. On the real dlog ladders, baby-step/giant-step against stride-4 is the second kind (raw median about 11.5 bits, no certifiable bound), and stride-4 against the reference is "A is faster, >= 1.54 bits".

Limits, in addition to the ones above and in the bundle's own README:

  • **Speed, unless the declaration defines quality().** A speed challenge has one cost number per instance and an all-or-nothing verifier; its cost is CPU seconds (any unit that plays the role of seconds against the 0.5 s floor works, for example scaled step counts). A challenge scored by the QUALITY of the answer at a fixed budget is a different kind with its own compiler and scorer: see "Quality challenges" below. A trade-off between the two (speed AND quality) is not expressible, and a quality challenge cannot run as a hosted round yet (only as a bundle).
  • **score.py does not know how costs were measured; check.py rerun tests them.** rerun --seed-file S --solver X.py --claimed X.jsonl --baseline REF.jsonl -k 5 re-runs a random sample (the verifier's own choice, printed) of the claimed instances on the verifier's machine, checks the answers, and compares re-measured with claimed speedup per instance; it also reports the machine factor and its spread, so a baseline ladder that was not measured on one machine shows up. On the real dlog stride-4 claims (seed d00100a7, 4 random instances, this Mac) the median claimed-vs-re-measured gap was 0.04 bit, machine factor +0.03 bit, spread 0.08. It samples (instances not drawn are not tested), cannot see a bias identical on every instance, is only as good as the hardware match, and its 2-bit default tolerance is loose because machine-to-machine spread has been measured only once (4 instances, one domain: median 0.01 bit, worst 0.03 bit between a Mac and a Linux server; see the Linux run below). score.py --out also records the sha256 of every input ladder and of the challenge, estimator and scorer, and score.py recheck RESULT.json recomputes and fails on any difference: tamper-evidence for a published number. A second sample on a different random seed (audit2, 3 instances, sandboxed, signed) gave 0.08 bit.
  • **rerun runs the solver in an OS sandbox by default.** No network, no writes outside a scratch directory, and the seed file, signing key, ~/.ssh, ~/.aws, ~/.gnupg and the keychain unreadable; the reference runs under the same wrapper so the overhead is comparable. macOS sandbox-exec is tested here against solvers that return a correct answer ONLY if they can read the seed, write outside scratch, or connect to a local socket (each is blocked; each succeeds with --sandbox off, so the tests are not vacuous). Linux bwrap was written blind, then run for real (see "The Linux run" below, which found a fifth bug, the vanishing CPU accounting). Reading it again, before it ever ran, had found four real bugs: --tmpfs /tmp hid every solver and bundle that lives under /tmp from the sandbox, the credential directories were not masked, there was no --new-session (the classic TIOCSTI terminal injection), and a bwrap that is installed but unusable (Ubuntu 24.04 restricts unprivileged user namespaces) was not detected. All four are fixed, and each is protected by a test that fails when it is reverted; the tests use a FAKE bwrap (a simulation of argv assembly, the verification probe and failure reporting, not of isolation). Every sandbox test used to be gated on macOS sandbox-exec, so on Linux they were skipped, never failed; they are now gated on "a sandbox actually works here" (Python is run under it once), so make test on a Linux box where bwrap works runs them for real, and the cheating solvers check file CONTENT (under bubblewrap a hidden file reads as empty rather than raising). On Linux the exec restriction is absent by design (network is unshared for every process instead). guldo's own Linux CI (GitHub Actions, per project notes) runs the suite and the Docker sandbox, which is a different mechanism; whether it has run this bundle code, and whether bwrap works on its runners, is not known to the author of this section (note that Ubuntu runners restrict unprivileged user namespaces, so install the distribution bubblewrap package and see the template). BUNDLE_LINUX_CI.yml.template is a ready job for it. Where no sandbox works, rerun refuses unless --sandbox off, and says why when the tool exists but cannot run. The profile also denies running any program except the interpreter's own installation (macOS framework Python re-executes itself through Python.app, so the whole base prefix is allowed): found by trying, because under the first profile a solver could still run /bin/sh and open(1), and open hands a URL to LaunchServices, which is network egress through another process. Tried and blocked now: a hard link, a symlink, a ../ path and a copy of the seed, cat of it through a child, curl, sh, open, and a unix socket to mDNSResponder; numpy still runs. Mach lookups are denied too (except Apple's user-name lookup service): this was the one documented hole, "a solver that calls macOS services through ctypes is not stopped", and it was real: a harmless bootstrap_look_up from inside the sandbox reached LaunchServices, the pasteboard, the preferences daemon and the directory service. Denying all of them broke pwd.getpwuid/getpass.getuser (they go through the directory service), so exactly that one service is allowed back; numpy's BLAS/LAPACK, threads and the numpy-heavy aiinfer domain (33/33 self-test checks sandboxed) are unaffected, and a real dlog rerun still reproduces to 0.01 bit. Tests: three services are reachable unsandboxed and denied sandboxed, user-name lookups and linear algebra still work, and removing either profile line is caught. A kernel exploit, or any service not reached through a Mach lookup, is still outside what this stops. It is not a proof of isolation: CPU time, memory and the kernel are shared, sandbox-exec is deprecated by Apple, and a solver can still burn its CPU cap. Found by running the real dlog solver: a solver given as a relative path stopped resolving inside the sandboxed scratch directory (every test had used an absolute one); fixed, pinned by a test, and a crash now prints the solver's stderr.
  • Signed attestations and a hash-chained log. check.py keygen, rerun --sign KEY --attest-out F, attest-check F... --trusted KEYS --min N [--claimed L --baseline L]: Ed25519 in pure Python (checked against the RFC 8032 vectors and against the cryptography library). A signature proves who signed, not independence from the operator, so only keys you pinned count as vouched (an operator can make five keys), one key twice is one party, an edited statement or a dissent turned into a pass no longer verifies, a valid signed dissent from ANY key fails the check, and an attestation for a different bundle or ladder is ignored. check.py log append|verify|checkpoint is an append-only hash chain (edit, removal, reordering caught). A truncated copy still verifies ALONE; log checkpoint LOG --key K --out C is a signed (head, count) that anyone can make and keep, and log verify LOG --checkpoint C fails for a log that no longer contains it, whether truncated or forked into a different but internally valid history (both tested). It only helps if someone other than the operator holds checkpoints and you pinned their key; the time is the logger's clock. Not a trusted clock, not trusted hardware, and guldo's own rounds and certificates remain the stronger protocol for adversarial settings.
  • No platform has reviewed this. Yukon's checker format is not public (its proposal form asks for a problem and a verifier description, and the checker is designed with their team afterwards), so the bundle targets nothing in particular. PROPOSAL.md is intake text, not an integration.
  • A bundle is code, so the tools that run it sandbox themselves. check.py derive|verify|selftest import and run the bundle's decl.py (and selftest its reference): by default they re-execute inside the OS sandbox (no network, no writes outside a scratch directory, ~/.ssh and friends unreadable). Tested here with a bundle whose decl.py writes a file outside the scratch directory at import, with every hash re-pinned so only the sandbox can stop it: blocked by default (reported as FAIL the declaration imports ... blocked by the sandbox?), written with --sandbox off. export_bundle.py verify --selftest also sandboxes and REFUSES to run where there is no sandbox unless --unsandboxed; plain check.py warns and runs as you there. Export runs its own self-test sandboxed, so a declaration that secretly needs to write files fails at export. Same limits as for rerun: not a proof of isolation, Linux bwrap simulation-tested only. The manifest hashes prove the files are the listed ones, not that they are safe. score.py runs nothing from the ladders it reads.
  • The verifier is tested, not proved. The self-test no longer rests on a fixed junk list: on the public practice seed AND a fresh random seed (printed; fixed from the declaration's hash during export so exports are reproducible) it also tries answers derived from each instance (every integer in the arguments, their neighbours, the argument list and its reverse), other instances' witnesses (a lookup table of past answers) and whether instances at the same index differ between the two seeds (a seed-ignoring derive() would make the commitment commit to nothing; an all-pairs witness-acceptance version of this diluted that to 6 of 36 and never fired, found by mutation testing), and damaged witnesses. Two kinds of damage are kept apart because one is legitimate: a witness with EVERY part damaged (all integers shifted, negated, zeroed) must be mostly rejected (more than half accepted fails), while a witness with ONE part changed only warns when accepted, since a verifier with a tolerance (aiinfer accepts up to 1% wrong labels) accepts those by design. The first version failed single-part damage and wrongly rejected aiinfer's export: a real false positive found by exporting a second domain, now pinned by a tolerance-style toy domain whose loosened twin (accepts any list of the right length, which no junk list catches) must fail. Tests also show it catches a verifier loosened to accept 1 and one loosened to accept n even when the file's hash was re-pinned. A verifier that accepts only something outside all of that still passes.
  • Dynamic imports and data files are found by running the declaration. Export runs it (import, then derive and verify three instances at every practice size, with the witness and a few junk answers) in a child process with an audit hook. It vendors every project or sibling module the declaration actually loaded, including ones the import walk cannot see (importlib.import_module("x"); listed under vendored_found_only_at_run_time), copies every data file it opened beside decl.py (listed under data_files, hash-pinned, relative to __file__ so it keeps working), and refuses with the file's name if it reads a project file that cannot travel. Still missed: a module or file used only on a code path none of those calls takes; the clean-interpreter self-test is the backstop. Data it reads from the network or a database is out of reach by construction. The reference may not import project modules (it runs in a sandbox that has only the standard library, numpy and fpylll).
  • **DRAFT is common today.** dlog exports as DRAFT because its declaration has no REFERENCE_NOTE and its compile record says the ladder was not confirmed; the bundle says so in its README and its proposal text.

Tests: test_export.py (compiles a toy domain, exports it, then drives the shipped files as a stranger would: moved to another directory, -I, tampering caught three ways, scorer equal to the project estimator on identical files, every refusal above, both compare verdicts).

Quality challenges (compile_quality.py, quality_core.py, qcheck.py, qscore.py)

A declaration that defines quality(inst, ans) -> float in [0, 1] is a quality challenge: every solver gets the SAME CPU budget per instance, and the score is how good its answer is, not how fast. Optimisation problems (max-cut, packing, scheduling), approximation and best-effort problems fit; "who answers first" does not.

extra declaration namemeaning
quality(inst, ans)called ONLY on answers verify() accepted (verify is the validity gate: any feasible answer passes); 0.0 = worst valid answer, 1.0 = best known or possible. Pure and deterministic. Typically min(1, value / best_known)
QUALITY_BUDGETCPU seconds per instance for everyone, the reference included (default 30; 1..600)
QUALITY_MIN_GAINthe smallest mean quality gain worth certifying (default 0.02 on the 0-1 scale; power is computed at this threshold)

python3 compile_domain.py compile NAME notices quality and runs compile_quality.py instead of the speed passes: the same parse and validation (two checks are relaxed: a no-search answer or another instance's witness may verify, as long as it scores at most 0.9, because in an optimisation problem many answers are valid and the score tells them apart), plus checks on quality() itself (finite, in [0, 1], deterministic on planted witnesses), then a profile of the REFERENCE's quality on the public profiling seed, which sizes keep headroom (a size where the reference averages above 0.95 is dropped; if none is left the compile refuses), the instances per size from a power simulation, and estimator controls (reference vs itself credits 0, a solver with no answers credits 0, a known gain is recovered). The record has "kind": "quality", and the domain is deliberately NOT registered as a speed family (families.DECLARED_ERRORS says so): the judge, harness and portal rank by the clock and would score it wrongly. Its product is the bundle: compile_domain.py export NAME.

The score (quality_core.py, shipped in the bundle as checker/quality_core.py): the paired difference of qualities, solver minus reference, per instance; the mean over each size, then the mean over sizes (equal weight per size); a conservative lower bound (the 1st percentile of a bootstrap that resamples instances within each size; a 5th-percentile bound measured 11-13% false credit per seed on real maxcut solves, this one 3.3%, with power unchanged: see ALPHA in quality_core.py); a seed's credit is max(0, lower bound); over seeds, the MINIMUM. An instance without a verified answer scores 0. Units are quality points: 0.05 = five points of the 0..1 scale.

The bundle ("metric": "quality" in challenge.json): checker/qcheck.py run runs a solver on every instance (sandboxed, CPU-limited to the budget; an answer that arrives after the cap scores 0) and writes the ladder; qcheck.py verify prints {"valid", "quality"}; qcheck.py qrerun re-runs a random sample of a CLAIMED result and compares claimed and re-measured qualities for the solver AND for the reference (a weakened baseline shows), failing on a large median gap OR on a signed mean above tolerance (a median alone passes a ladder in which up to half the claims are invented; found by a test), signed with --sign like rerun; checker/qscore.py has score, compare, power, recheck (stdlib only). check.py selftest tests verify and quality(); its speed-only commands (rerun, spread) and score.py refuse on a quality bundle.

Worked example: domains/maxcut (planted-partition max-cut; reference = one random assignment plus one greedy sweep, quality about 0.85). Run for real: a simulated-annealing solver scored a credit of 0.12-0.14 on three seeds (mean gain +0.13, better on 60 of 60 instances), an all-zeros cheater and the reference against itself scored 0, compare separated the two, recheck reproduced the result, and qrerun confirmed the honest ladder and failed three lies (inflated claims, a weakened baseline, a different solver).

What this does NOT do:

  • **quality() is the author's, and the score is only as good as it.** The tools check its range, determinism and that no answer needing no search scores above 0.9; whether it measures what you care about is not checkable.
  • The noise in the power table is an assumption (equal to the reference's own within-size spread, floored at 0.02). One real pair (maxcut, annealing vs reference): observed 0.036 against a reference spread of 0.02-0.04. qscore.py measures the real value and re-simulates when it is clearly higher.
  • Machine speed changes the score. An anytime solver does more per CPU second on a faster machine; qcheck.py run records a machine calibration (CPU seconds of a fixed pure-Python workload; 0.099-0.104 s over six runs and 0.103 s under four CPU hogs on the Mac) in each ladder, and qscore.py refuses to compare ladders whose calibrations differ by more than 1.25x (--lenient: PROVISIONAL), while qrerun says when the verifier's machine differs. That catches a machine mismatch, it does not correct for one, and it is pure-Python speed (a numpy-bound solver may scale differently). A qrerun that fails on a machine of a different speed is INCONCLUSIVE (exit 2), never signed (found by running an honest solver on slower cores: it FAILed, and --sign would have signed a dissent against it); a claimant can force INCONCLUSIVE with a false calibration, so INCONCLUSIVE is not PASS. qrerun --save + qcheck.py qspread measure the spread. Measured so far, on ONE chip: a time-limited annealer on an Apple M4 Pro's performance vs efficiency cores (calibration 5.3x apart) scored up to 0.12 lower (median 0.08) on the slow cores, the fixed-algorithm reference 0; recommended tolerance 0.11-0.13 over repeats (the slow-core run varies), above the 0.05 default. Same chip, same cores, two runs: spread 0.01. The INTERPRETER matters as much as the hardware: the same solver on the same cores under Python 3.9.6, 3.12.9, 3.13.7 and 3.14 had calibrations 1.53x, 1.08x, 1.35x and 1.0x of the 3.14 reference run, and quality spreads against it of 0.10, 0.02, 0.03 and 0.01, so the calibration ratio tracked the spread in all four (and the 1.53x and 1.35x runs would be refused by qscore.py, which is the 1.25x rule working; four points, one solver, not a calibration curve). That is two CPU classes of one chip, NOT two machines: real cross-machine data needs another host (the check kit's quality/run_quality_on_linux.sh, with the Mac's measurements already in it; not run elsewhere). The 0.01-bit result for speed ratios is a different thing: ratios cancel machine speed.
  • Budget enforcement is CPU time of the process tree with the speed bundle's detection of hidden CPU (a run over a second of wall time with under 30% as CPU is scored 0 / failed); a solver that hides under 70% of its CPU is not caught. A solver that leaves a detached process behind (a hidden helper) is found by run_solver's process scan (added by another session for the speed rerun; found missing from the quality tools by an audit): run scores that instance 0, qrerun FAILs on any machine and never calls it INCONCLUSIVE; with no ps the scan cannot run and the tools say so (and process_scan: false goes into a signed attestation).
  • No hosted round. There is no quality counterpart of rounds.py, ops.py or the portal; a quality challenge exists as a bundle only. A speed-AND-quality trade-off is not expressible.
  • Less tested than the speed path. test_quality.py (58 tests; 45 planted bugs in the statistics, scorer, rerun rules (including INCONCLUSIVE, signing and qspread), selftest checks, registration guard, validation relaxation, machine calibration and output handling were all caught, after seven survivors that were test gaps and were fixed; the scorer, qcheck and recheck inputs were also fuzzed: ladders, result files and options, 0 tracebacks) and one real run on one machine; no platform has reviewed a quality bundle; the Linux sandbox path for run/qrerun is exercised only by the speed tests' bwrap probes and the new bundle-linux workflow, which has not run on GitHub.

The pre-registered real-solver test (dlog_experiment.py)

results/PREREGISTERED_dlog_realsolver.txt was written before any data existed: two real dlog solvers (a 4-entry baby-step scan, true speedup about 1.3-1.6 bits, and full baby-step/giant-step, far above the ceiling) on three seeds. python3 dlog_experiment.py applies its criteria mechanically from the saved ladders and claim files (and re-hashes every registered code file, failing if any changed), and the Results page shows the same table. Criteria that cannot be evaluated yet print PENDING, never PASS.

What this does not do (read before relying on it)

  • A certificate proves consistency, not honest measurement. It shows the commitments were public first, the instances are the seeds' own, the rules are the named ones, and the credit follows from the records. It cannot show the CPU costs in those records are what a sandbox measured: an operator could write plausible ones. Only the Docker meter (unverified), verify --rerun (re-measuring instances yourself, needs --execute) and independent attestations from keys you chose to trust address that, and the first of those has never been run on a real host. build --reveal-seeds is refused until the round is revealed.
  • A private solver is hidden from the public, not from the operator. certificate.py make-private (or build --private; in a round, any submission whose owner did not choose "publish source") removes the solver's source and every failure message from its ladders (a traceback quotes code). The log, the fingerprints, the questions, the rules and the credit arithmetic still verify, and the solver's hash is the one the round's log committed to before the seeds were revealed; but nobody except the operator can inspect or re-run it, so its timings rest on the operator's sandbox alone (the verdict says so). If the owner publishes the file, verify --source FILE checks that it hashes to the committed value and, with --rerun --execute, re-measures it: the certificate is then as strong as a full one. Hiding a solver from the OPERATOR too would need trusted hardware (not available) or a zero-knowledge proof of execution, which is infeasible here: these solvers run for seconds to minutes (billions of cycles), a zkVM would count abstract cycles not CPU seconds, and it cannot run numpy or fpylll.
  • The reference defines the baseline. A certificate says "faster than this reference by this many bits on its hardest instances". It does not say the reference is a good algorithm. A weak reference makes big speedups cheap; the compiler cannot judge that and neither can the estimator. What it does is make the author say it: a missing REFERENCE_NOTE makes check warn (it does not fail), and the note is copied into the compiled record, the challenge document and the domain card, and reads "not stated" when missing. When someone beats the reference by a large margin, replace the reference, bump VERSION and recompile; old results then refuse to mix with new ones.
  • The power analysis rests on an assumed pair noise. Real per-instance noise of a submission against the baseline cannot be known before a submission exists. The default is 0.6 bit (--pair-noise); compare it with the measured values in PROTOCOL.md and re-run with yours. The compile also fixes everything from 8-instance medians per size, so the ladder is a good choice, not an optimal one.
  • Certifiable range has a ceiling (about 5 bits at a 120 s cap, as in PROTOCOL.md): a solver that is 2^5 times faster than the reference costs less than the estimator's 0.5 s floor on the instances the baseline finds hard. The compiled CHALLENGE.md reports the actual range; beyond it a model baseline is needed (not built).
  • Validation finds the defects it knows. The anti-cheat checks catch a verifier that is guessable, derivable from the arguments, or reusable across instances. They cannot prove a domain has no shortcut: a domain whose instances are structured so that a solver can skip the work is the author's to rule out (EGG.md is the worked example of a family that could not be tested).
  • The sandbox is still unverified. Everything here inherits sandbox/README.md: the Docker meter has never passed test_sandbox on a real host, so no compiled domain can have an OFFICIAL result yet, exactly like gm, mlwe and factor.
  • The self-test is local mode. It runs at the chosen official n (--selftest-n lowers it to save machine time, but a known-effect control run below the n the power analysis chose can fail for lack of power alone), without Docker. It tests that the compiled pipeline behaves; it is not an official run.
  • **What the compiler's notes caught on dlog.** The reference's cost does not double smoothly per size: size 30 measured a 39-43 s median against 3.4-3.8 s at sizes 28-29 (twice, with 8 and with 16 instances), a cliff that is probably CPython's big-integer arithmetic leaving its single-digit fast path once the modulus passes 2^30. The compile re-planned to a 3-size ladder (28-30, 2.6 octaves), and its output says so: "narrow ladder", "NOT independently confirmed", "still off by more than one octave at size 30". It did not hide the cliff or claim a confirmation. The honest reading is that this reference is a poor baseline for a ladder (a perfectly valid, deliberately plain demo), and that a declaration author should read those notes, not just the exit code.
  • The dlog challenge's size-29 profile is slightly optimistic. Its compiled record dropped one slow instance and counted another twice, so the recorded size-29 median (3.75 s), spread and the ladder chosen from them lean toward cheaper instances. How far is not measured (that needs all 16 instances at the 120 s cap). Recompiling the domain settles it; that is held until the pre-registered experiment ends, because the compiled record is part of what that registration hashed.
  • The profile is noisy. The ladder and the power simulation rest on 8-instance medians per size (--n-prof). On the first real run (dlog) neighbouring sizes came out as 3.7 s, 2.05 s and 43 s where the true cost doubles per size, so the compile re-plans, and the resulting ladder can be short (3 sizes there) and irregular. Raise --n-prof for a steadier profile.
  • Python 3.14 here. Tested on the interpreter at hand; 3.10-3.13 and Linux are untested like the rest of the project (PROTOCOL.md).
