Limits

What this does not show

The most useful part of a verification site is a list of what it has not verified. This page is kept as plain as the results.

What a checked result still does not prove

A certificate can be checked by anyone, and checking it proves the arithmetic and the fairness. It does not, by itself, prove the timings were honest.

  • Proven by checking: the seeds' fingerprints were public first, the questions are exactly the ones the seeds produce, the rules are the ones named, and the credit follows from the recorded timings.
  • Not proven by checking: that the recorded timings are what a real run took. Someone who runs the test could write plausible numbers. What helps: the locked-box environment (its tests have passed on real Linux machines, but no official result has been measured in it yet), and other people re-measuring on their own computers. A re-measurement only counts as independent if you chose to trust whoever made it: a signature shows who signed, not that they are unconnected to the operator.
  • One way to prove a cost exactly: instead of seconds, count the Python instructions a solver executes. That number is the same on every computer, so anyone can re-run a few questions and must get identical counts, trusting nobody's machine or clock. It has limits: it is not a time, it cannot see work done inside a built-in C function (which counts as one instruction however long it runs), it needs a recent Python and pure-Python solvers, and, unless a counted round declared the sizes in its first log entry before any submission, the question sizes are chosen by whoever ran it, so it is not an official round result.
  • AI workloads carry weaker evidence than the lattice and factoring ones: a counted-operations certificate proves how much arithmetic a solver asked for, not how fast it ran, and cannot see memory traffic, precision or kernel quality. A timed AI speedup depends on the machine's numerical library: the same float32 solver measured about 3.3 bits on a Mac and about 0.03 bits on a Linux server. A GPU time is one operator's clock on one device model and cannot be re-executed exactly by anyone else. See AI workloads on the Domains page.
  • The baseline decides what counts: a speedup is only as meaningful as the solver it beats. A weak baseline makes big speedups cheap. Each problem's author is asked to say what the baseline is and what is known to beat it, and the problem's card shows when they have not.
  • Computers differ: a speedup is a ratio, which mostly cancels differences in machine speed, but the spread across different machines has not been measured yet, so the tolerance for re-measurement is deliberately loose.
  • Private solvers are hidden from the public, not from the operator: a submitter may keep their solver private, and then the public certificate shows only its fingerprint. Everyone can still verify the log, the questions and the arithmetic, but nobody except the operator can inspect or re-run it, so its timings rest on the operator's sandbox alone. If the owner later publishes the file, anyone can check it against the fingerprint. Hiding a solver from the operator as well would need special hardware or a zero-knowledge proof, and neither is feasible for solvers that run for minutes.

Open limits

  • The Docker sandbox that makes it safe to run other people's code has passed its tests on real Linux machines, but not on a dedicated evaluation machine separate from the web service, and no result on this page was measured in it. Every run on this page used bare local processes and the project's reference solvers, so none of it can be an official result.
  • Official credit needs three independent seeds, each with a published commitment, the sandbox, and the family's full instance count and CPU cap. No seed on this page meets all of those.
  • The credit rule was designed while looking at an early design run's data ("seed A" in the registrations on the Pre-registrations page), so that run is not an independent test of it. The out-of-sample test is a pre-registered run on a fresh seed, with its pass criterion written down before the data existed.
  • The certifiable range is limited. At the official ladder (24 instances per size, 120 s cap), a simulation with real per-instance noise certifies a constant speedup of 1.5 to 3 bits with roughly 65 to 100% probability (each figure is good to about 10 points), 1 bit rarely (6.5%) and 4 bits almost never (1%), because too few hard instances remain for the bound to stay stable. A round can ask for more instances per size (48: 68% at 4 bits; 96: 100% at 4 and 98% at 5 bits), but about 5 bits is the ceiling at a 120 s cap whatever the count, since a very fast submission falls under the 0.5 s cost floor wherever the baseline finishes. Results outside the range are reported as inconclusive, never credited, and speedups of tens of bits cannot be certified by this design at all.
  • The lattice-attack code from the paper that made the original speedup claim cannot yet serve as a baseline: its sieve does not reach the target size past dimension 30.
  • The lattice competition does not include or test the "egg". The egg is a separate analysis's claim that the searches used against lattices cover an egg-shaped region rather than a sphere, which it says could mean a very large saving at the sizes real encryption uses. That is its authors' own estimate; the project has already claimed it in that analysis and does not count it again here. This competition does not measure it, and does not confirm or refute it. It looks for gains that do not rely on that effect: credit here is only a measured lower bound on the speedup over a named baseline (stock block reduction, sizes 64 to 72), which is not the kind of search the estimate is about, so the two numbers are never added or compared. Entries that use the same effect are measured and published but reported as inside the egg, not as new, and are not added to each other. Only entries confirmed to be independent of that effect are reported as such.
  • Several jobs at once can bias a result. The runs on this site used several processes on one computer at the same time. Re-measuring one job at a time shifted the baseline by -0.050 bits and the tuned solver by -0.084, so the speedup was slightly underestimated, not inflated. The pass line was a shift under 0.10.
  • The bias depends on the solver, and one check failed. On the factoring control, re-measured one job at a time, the baseline (a plain Python loop) moved by -0.033 bits, but the numpy solver ran 1.16 bits faster than it had with six jobs at once, against a pre-registered limit of 0.10. The bias happened to favour the baseline, which makes the credit cautious, but for another pair of solvers it could point the other way. So runs with several jobs at once are valid only after re-measuring both sides one job at a time, and official runs use one question at a time in the locked box.
  • The factoring control is not a clean recovery of a known number. Its known effect (about 4.4 bits) was calibrated on 44 to 52-bit numbers. The 4.2 bits measured at 58 to 64 bits agrees with it partly because the several-jobs bias cancels a real increase with size.
  • One seed is one sample. The pre-registered result is a single test on a fresh seed, not a replication.

Related work

Public challenges already exist in this area. The Darmstadt SVP challenge and its LWE counterpart publish instances and record solutions. Yukon, from Eigen Labs, is an open platform where people and AI agents compete on posted technical challenges. This project is about checking claims: seeds committed before the questions exist, a public log, and certificates anyone can recompute.
