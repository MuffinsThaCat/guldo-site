Audit history

How the checking tools were tested

Each claim the tools make was attacked before it was relied on: bounds were measured by simulation, the test suite was mutation-tested, and the sandbox was run on a real Linux machine. This page is the round-by-round record, generated from COMPILER.md. It is history, not instructions: the working reference is the Guide.

  • Machine-to-machine spread now has a tool, and the within-machine part is measured. rerun --repeat N re-runs each sampled instance and reports this machine's timing repeatability: on the real dlog claims (4 instances x 3 runs) the median sd of log2 cost was 0.009 bit for the reference and 0.005 for the solver, and the claimed-vs-re-measured gap on that sample was 0.02 bit, so the 2-bit default tolerance is two orders of magnitude above same-machine noise. What is still NOT measured is cross-machine spread: rerun --sample-seed S --save F on each machine (same seed everywhere; the machine is stored as a hash, never the host name) and check.py spread F1 F2 ... give a recommended tolerance (the worst observed range rounded up to a quarter bit, never below 1; an estimate, not a bound), refusing with fewer than 2 distinct machines or 3 shared instances rather than inventing one. A real two-machine measurement now exists (Mac vs a Linux server, see the Linux run bullet), but it is one domain and four instances: it supports, and does not set, a tighter tolerance.
  • Checked on other interpreters and from the installed package. check.py (standard library only) passes its full self-test on Python 3.9, 3.12, 3.13 and 3.14, sandboxed. A scoring result made on 3.14 / numpy 2.3 rechecks identically on 3.9 / numpy 2.0 and on 3.12 / numpy 2.4 (the estimator's bootstrap is seeded, and recheck compares to 1e-9). The package was staged, installed into a clean virtual environment and used from there; that found that the documented guldo export NAME did not work (the packaged tool routes straight to export_bundle.main, which wanted export NAME). Fixed, and pinned by a test that runs the documented short form. Not run: an installed package on Linux, or Windows (rerun needs POSIX resource).
  • The 95% lower bound was measured, not assumed. Through the real estimator (400 bootstrap resamples) on ladders drawn from dlog's compiled profile, 1500 trials per cell, the credit exceeded the TRUE speedup in 0.9% to 3.3% of trials across true effects 0 to 3 bits and per-instance noise 0.3, 0.6 and 1.5 bits (nominal limit 5%), and exceeded it by more than a quarter bit in at most 0.4%. The median credit sits 0.1 to 0.7 bit below the truth: the bound is valid and conservative, under the model that generated it (log-normal baseline costs, Gaussian pair noise). It says nothing about heavy-tailed real noise beyond what the real dlog ladders show.
  • The test suite was mutation-tested. 43 deliberate bugs (an Ed25519 verifier that always accepts, a log that ignores broken links, each sandbox rule removed in turn, max instead of min over seeds, a scorer that accepts truncated ladders, an exporter that skips its own self-test, ...) were applied one at a time to a copy of the project and run against the tests meant to catch them. First run: 7 survived, i.e. real test gaps: nothing tested that the credit is the MINIMUM over seeds (every test used identical seeds), that a log edit with a recomputed hash is caught by the next entry's link, that a solver wrong on only SOME instances fails, that a bundle with an extra unlisted file is flagged, that export really runs its own self-test, that the every-part-damaged check is the one that fires, and the cross-seed check. The last one turned out to be a design flaw: it compared witnesses over all instance pairs, which diluted a seed-ignoring derive() to 6 of 36 pairs (below the 25% warning), so it could never fire where it mattered; it now compares instances at the SAME index. All 7 are fixed with tests that name what they pin, and all 43 mutations are killed. Mutation testing finds gaps in tests, not bugs in untested paths: the 43 are the paths that were thought of.
  • The Linux run (11-21, one Hetzner server: Ubuntu 26.04.1, kernel 7.0.0, 2 vCPU, Python 3.14.4, bubblewrap 0.11.1 extracted from the distribution package into a temp directory, nothing installed system-wide). A check kit did four things. (1) The sandbox holds. An attack probe run sandboxed AND unsandboxed (so a vacuous probe shows): the seed, ~/.ssh, an outside write, a loopback socket and a hard link to the seed were all blocked, an in-scratch write worked, and running another program was allowed (by design on Linux). The bundle self-test passed 62/62 through bubblewrap; 63 unit tests (sandbox, meter, FIFOs, flock, attestations, checkpoints, data files) passed with bubblewrap in use, 3 skipped (macOS-only). (2) The first run found a real bug that no amount of reading would have: under bwrap --unshare-pid the kernel's CPU accounting for the program VANISHES (a 2 s burn read as 0.00 s with --unshare-pid, 2.03 s without it). Every rerun on Linux "measured" ~0 and still printed RERUN PASS (the claims were small enough to sit inside the 2-bit tolerance), and the "1.5 bit" spread it produced was garbage and was discarded. Fix: --unshare-pid --as-pid-1 (the program runs as the namespace's init, no reaper in between) keeps both the accounting (2.03 s) and the PID namespace; the CPU cap (kills at cap+1 s), the wall backstop and the orphan cleanup (a forked CPU-burner dies with the namespace) were verified on the real kernel. Added so this can never pass silently again: rerun refuses when an empty Python start measures under 2 ms, FAILS when the reference reads ~0 where its published cost is seconds, and a kill reported as exit 137 is a timeout, not a crash; each is protected by a test that fails when reverted. (3) Unprivileged use needs the distribution's bubblewrap: as the unprivileged user, the copy running from /tmp failed with loopback: Failed RTM_NEWADDR: Operation not permitted (Ubuntu's AppArmor user-namespace policy ships a bwrap-userns-restrict profile for /usr/bin/bwrap; the extracted copy was not covered). The tools diagnosed it exactly as designed (the reason in a warning, or a refusal when a sandbox is required). The package was not installed. (4) The first real cross-machine measurement: four published dlog claims re-measured on an Apple M4 Pro (macOS) and on the server (about 0.5 bit slower in raw speed) agree on the re-measured speedup to a median 0.01 bit, worst 0.03 bit (Mac +1.34/+1.35/+1.36/+1.35, Linux +1.37/+1.34/+1.36/+1.35; spread recommends its floor of 1.0 bit). Limits of that: 4 instances, one pure-Python domain, one solver family; BLAS-heavy work may differ, so the default tolerance stays at 2 bits. Side effects to know about: a timed rehearsal round (a docker run of baseline_bkz from /srv/ledger/rehearsal) was running on that server at the time; the probes used about 30 CPU-seconds at lowest priority alongside it, so whether that rehearsal's timings need repeating is a judgement to make. Everything placed on the server was deleted and its services were untouched.
  • **CPU hiding against rerun (found by attacking the fix, not by reading it).** The meter guards from the Linux run only catch a meter that reads ~0. A solver can also HIDE its CPU: fork the real work into a child and return the answer through a pipe WITHOUT waiting for it. Linux credits a child's CPU to its parent only when the parent waits, so on the real server (no sandbox) 2.0 s of work measured as 0.02 s: the attack works there, and a fabricated speedup would reproduce. macOS credits CPU at the child's exit, so the same solver was measured honestly there (real dlog ladders, a fabricated 2048x claim: the hider's CPU was counted), which is why this had never shown up. Under bwrap --as-pid-1 it is already closed (the kernel reaps everything in the namespace when its init exits, rolling the CPU up: measured 2.03 s), so the exposure is --sandbox off on Linux. The defense does not depend on the OS: rerun now compares each run's CPU with its wall clock and FAILS the claim when a run took over half a second of wall time with under 30% of it as CPU (first version said one second; the next audit measured 0.6 s and 0.9 s of hidden work passing it, and lowered the minimum to the estimator's own 0.5 s floor, below which costs cannot move a score) (a CPU-bound solver cannot do that honestly; one that waits, or whose work runs where the meter cannot see, can). Tests: a stand-in that waits is failed with a 50-bit tolerance (so only this check can fail it), an honest CPU-bound solver is not flagged, the one-second minimum and the 30% boundary are pinned, and each part of the logic is caught when disabled. SECOND DOMAIN, THE OPEN TOLERANCE ITEM (11-21, measured, "do open items"): the Mac-vs-Linux agreement of 0.03 bit does NOT generalise. aiinfer (numpy/BLAS; solvers/aiinfer_f32.py vs the float64 reference; own practice seed, 3 instances at d=2304; the round's real seed is not kept in the project, only its commitment) re-measured +3.27/+3.37/+3.46 bits on the Mac (matching the published ladder's +3.3) but +0.03/+0.03/+0.03 on the Linux server: spread = 3.34 bit median, 3.42 worst, recommended tolerance 3.5. Cause, located by profiling: instance generation is cheap on both (0.12 s); the time is inside the solver's own numpy calls (0.07 s on the Mac, 20 s on the server), and a plain float32 matmul runs at 815 GFLOP/s on the Mac (Apple Accelerate) against 18 on the server (single-thread OpenBLAS, EPYC Genoa VM), 46x; the solver is a further ~7x slower on the server than a bare matmul predicts (NOT diagnosed; denormal arithmetic, which Apple silicon flushes and x86 does not, is a candidate). At d=3840 every run, reference included, hit the 30 s CPU cap on the server. Consequence: a speedup is a ratio of two costs and the ratio is machine-class dependent for BLAS-bound work, so (a) the default tolerance stays 2 (right for pure Python, 0.03 bit measured) but is documented as too tight for numpy domains, (b) rerun now prints a NOTE when this machine's reference differs from the claimant's by 1 bit or more (mutation-tested), and (c) the recommended practice is to re-measure on a machine like the claimant's or to run spread. Not done: making the tolerance domain-aware automatically (would invent a number from two domains). Next audit (spread): --save recorded neither the solver nor the seed, so spread could merge measurements of two different programs, or of "20:3" under two seeds (a different instance), and call the gap machine-to-machine spread; and a run that failed the hidden-CPU / detached-process / dead-meter checks still saved its numbers. Saved files now carry solver_sha256, seed_commit, rerun_checks and untrusted_instances; spread ignores a file whose solver or seed differs from the first, leaves out flagged instances (and says how many), and notes (but still uses) older files that record neither. 5 new mutations (E1-E5), all killed. Files from before this change (the kit's mac.json, linux.json, aiinfer-*.json) are of the older kind and are used with the note. SUPERSEDED (11-21, later the same day, after a third domain): aidecode (numpy, small d=128 kernels, aidecode_kv_f32.py vs the recompute-everything reference, own practice seed, 3 instances at T=544, Mac vs the Linux server, saved with the new solver/seed identity) re-measured +5.28/+5.19/+5.30 bits on the Mac and +7.37/+7.37/+7.31 on the server: spread 2.09 median, 2.18 worst, recommended 2.25, and the sign is the OPPOSITE of aiinfer's (the server's reference is 8x slower, 27 s vs 3.4 s, its solver only 1.8x slower) so no single correction factor exists. Caveat: the solver costs only 0.09-0.16 s, under the 0.5 s floor the scorer ignores, so timer noise is larger there; T larger than ~550 puts the server's reference over the 30 s cap. With three domains on one machine pair (pure Python 0.03, numpy 2.18 and 3.42 bits) the decision changed: the default tolerance is now 2 bits for pure Python and 3.5 bits when the manifest's requires.third_party names a numerical library (numpy, scipy, torch, jax, tensorflow, numba, cupy), printed before measuring, overridable with --tolerance, and recorded in the attestation (3 mutations killed, plus a real command-line test). The cost is stated in the output: a looser tolerance also lets a larger false claim pass, which is why spread on the verifier's own machines remains the better practice. One machine pair is still one machine pair. Next audit (the looser default): a PASS at 3.5 bits accepts a false claim up to 3.5 bits off, but attest-check neither showed the tolerance nor let a reader limit it. It now prints "tolerance used" (with what that means) for every rerun attestation, and --max-tolerance BITS makes a PASS at a looser tolerance, or one whose tolerance is missing, non-numeric, boolean, negative, NaN or too large to read, not count; a valid FAIL always counts. 6 mutations (G1-G6). Three things this round's tests taught: (1) the first mutation run left one alive because the test asserted the summary phrase "valid dissent", which is printed with a count of 0 too, so it was rewritten so the dissent is the only thing deciding the outcome (and a second test with the same weakness was strengthened); (2) the fuzz test then found a REAL crash in the new code: a signed attestation with an integer tolerance of 10**400 raised OverflowError in attest-check (fixed, pinned by a deterministic case); (3) the new command-line test asserted a rerun verdict that is timing noise for few-millisecond runs and failed under load (reproduced at 2x oversubscription, fixed by asserting only what the test is about; 5 of 5 runs of the affected classes pass at 3x). Earlier decision, now superseded: keep the 2-bit default, because the only evidence is two domains and any other number would be invented; instead the warning is now proactive. rerun reads the manifest's requires.third_party and, for a numerical library (numpy, scipy, torch, jax, tensorflow, numba, cupy), prints before measuring that speedups of such work depend on the machine class, quotes the measured Mac-vs-Linux disagreement, and points at spread and --tolerance (a pure-Python or non-numerical challenge gets no note; 2 mutations killed). Revisit the default only once a third domain is measured on two machine classes. Other open items, decided: no system package is installed on the production server (an owner-level change, and root use already works with the extracted bubblewrap), nothing is sent to any platform, and the harness.py post-run note stays as written pending the owner's confirmation.

DETACHED PROCESSES (next audit, found by asking what the solver and reference SHARE): a solver that setsid()s a child and closes its stdio returned in 0.03 s and left the child running, burning CPU through later runs, measured on macOS WITH the sandbox on (with stdio open the harness just waited 8 s on the pipe). It could slow the reference's next run, or serve later instances as a hidden helper whose CPU is nobody's. Now: each solver run gets its own session and the whole process group is killed after it (catches children that exec something else); orphans of this exact solver file still carrying the runner's command line (parent = init, not present before the run) are found and killed by exact pid (never a pattern, never a live process, never another solver's); and rerun FAILS the claim ("left a detached process"). Verified: the probe's child is dead 1.5 s later in both sandbox modes; 5 mutations of this code killed; on the real Linux server the changed run_solver still measures CPU correctly (41 meter/sandbox/rerun tests pass with bwrap). Next audit: with no ps (slim containers) the scan used to return "none found", so a detached child kept running and nothing said so (measured); the scan now returns "could not run" for a missing or failing ps, a run records it, rerun prints a WARNING that detached processes could not be checked (the group kill and bwrap still apply), and a scan that failed on only one side never turns pre-existing orphans into "this run's strays" (they would have been killed). 5 mutations killed. Next audit: the --repeat runs (noise measurement) skipped both checks, so a solver could behave on its scored run and detach or wait only on the repeats; they now go through the same stray and hidden-CPU rules (2 mutations killed). Measured cost of the scan: about 71 ms per run (96 vs 25 ms), roughly 0.9 s for a 3-instance rerun, outside the CPU measurement; detection works on paths with spaces, accents, parentheses and a 378-character path. Re-verification of the "43 mutations, all killed" claim against the CURRENT code (the checker had changed a great deal since it was written): three of the patterns had gone stale (the ok = verdict line, its tolerance line, and the DRAFT-status check, which now exists twice because the quality exporter copied it) and were rewritten; one clean, single run of all 43 then killed 43, survived 0. An earlier pair of runs reported 3 survivors (log checkpoint containment, attestation challenge binding, export overwriting a directory); each is killed when run alone, and the likely cause was operator error: a first launch of the runner may have kept going in the background while a second ran, so two runners rewrote the same copy and restored files under each other's tests. Lesson recorded: a mutation harness must run exactly one at a time on its own copy, and a "survivor" is only real once it survives alone. The mutation runner is now in the project: mutation_check.py (make mutation [IDS="C14 X5"]), 57 mutations (the 43 plus 14 for the rerun defences and the spread/save logic added since; the last full run was 50 of 50, the 7 newest were run on their own), built around the mistakes above: it mutates a private snapshot, never the live tree; holds a lock so only one run happens at a time (a dead owner's lock is taken over); runs the unmutated tests first and refuses to report if those already fail; reports a pattern that no longer matches exactly once as BAD-MUTATION instead of skipping it (TestMutationTool also fails the suite when a pattern goes stale); and exits 1 on any survivor. Its guard rails are themselves mutation-tested (4 of 4 killed). Its first full run proved the baseline step worth having: the UNMUTATED tests failed, because one of the tests asserted that a real 1.2 s burner keeps at least 30% CPU share, which a busy machine (other test suites running) does not give; it now judges a second run of the burner against the first, as the real rule does (passes 4 of 4 under 3x CPU oversubscription). The run after that: baseline PASS, 50 of 50 mutations killed, exit 0. Next audit (attestations): attest-check ignored the signed sandboxed field and could not tell an attestation made before the CPU-hiding / detached-process checks from a current one, so an unsandboxed or old-tool PASS counted like a full one. Statements now carry rerun_checks (2) and process_scan; attest-check prints "weaker evidence" for an unsandboxed run, an older tool, or a skipped scan, and the new --strict refuses to count such a PASS (a FAIL always counts; 4 mutations killed, the bool-as-version guard was dead code and removed). Honest limit: these are the signer's own claims; an attacker holding a pinned key can write rerun_checks: 2 without running anything, which is why only pinned keys count at all. Limits: a solver that detaches AND renames its process title, or execs after setsid, escapes the macOS scan (not the bwrap namespace on Linux, which kills everything); the scan relies on ps and on orphans being re-parented to init (a Linux user-systemd subreaper changes that, which bwrap covers). SUPERSEDED BY THE RELATIVE RULE (next audit, "figure out what's not closed"): the fixed 30% share is now only the fallback. Each instance's solver run is judged against the reference's share on the SAME instance (flag below 60% of it, the share capped at 100% so a threaded reference does not raise the bar; used only when the reference ran over 0.5 s; the reference itself is flagged only under 15%). Verified on the real Linux server with the padding attack: reference 100% share; padders at 29%/34%/42% share faked 1.3/1.0/0.5 bit, and the fixed rule missed the last two, the relative rule flagged all; on a loaded machine both runs starve alike so an honest solver passes (a wired-in rerun test with a 28%-share reference and solver: PASS). What a solver can still hide: it must stay above 60% of the reference's share, so at most 1/0.6 = 1.67x = 0.74 bit. 7 mutations of the rule, all killed. The two limits below (false positives under load, the 1.7-bit padding bound) described the FIXED rule and are now closed down to that 0.74 bit, except that a load that hits the solver's run but not the reference's (a burst between the two runs) can still false-flag, which fails safe. Original re-audit, measured: (a) FALSE POSITIVES: an honest 1.5 s burner kept 97% CPU share idle, 78% with as many busy competitors as cores, but only 28% (flagged) with 3x oversubscription, so a heavily loaded machine fails honest solvers; the verdict is the safe side for a verifier and the failure message now prints the load average and says to re-run when idle. (b) BOUND on the evasion: a solver can pad its parent's CPU to just over 30% of wall and hide the rest, which fakes at most about 1/0.3 = 3.3x, i.e. 1.7 bits, inside the 2-bit default tolerance; so this check closes the large fakes (the 2048x one) but not a 1.7-bit one. Tighten with --tolerance below 1.7 if that matters, or keep the sandbox on (bwrap --as-pid-1 counts everything). Limits: a solver that hides only PART of its CPU (say half) stays above 30% and is not caught; --sandbox off on Linux is for solvers you trust; a solver that waits for a legitimate reason (I/O) would be wrongly failed, which is the conservative side for a verifier.

  • Re-audit of the Linux changes. (1) An earlier fix regressed performance: the "does the sandbox actually work" probe added to every selftest/derive/verify re-exec raised the sandboxed call from 135 ms to 180 ms (the documented 75 ms overhead had become 120 ms). The probe is now only used where it runs once (rerun, and the tests' gating); the hot path runs the real command and diagnoses a sandbox TOOL that could not start by its own error line (bwrap: ..., sandbox-exec: ...), not by any non-zero exit, so a wrapped command's own failure is passed through and never re-run unsandboxed. Back to 58 ms unsandboxed, 135 ms sandboxed; both the "never diagnose" and the "diagnose every failure" mutations are caught. (2) The CI template would have shown green on failing tests: ... | tee log reports tee's exit status unless the shell is bash with pipefail (a step needs shell: bash explicitly). Fixed in BUNDLE_LINUX_CI.yml.template. (3) Seed and solver paths with spaces, accents and parentheses were never tested against a profile built from path strings; they work (a cheater is blocked and, unsandboxed, leaks, so the test is not vacuous), and a test pins it. The first attempt at that check was vacuous (a factoring cheater against the dlog domain crashed even unsandboxed); it was caught because the comparison arm did not leak. (4) The non-blocking open no longer assumes os.O_NONBLOCK exists.
  • Concurrency and hostile paths (the next round of auditing the audit). (1) Eight simultaneous log appends wrote 4 entries, broke the hash chain and refused the other 4 submissions: read, verify and write were three steps with no lock. Appending now holds an exclusive flock from read to fsync (reads take a shared lock so they never see a half-written line); 24 concurrent appends all land with a valid chain, a 16-way test pins it, and removing the lock in a copy is caught. Needs POSIX; elsewhere an append refuses. (2) Every tool that read a file named on its command line hung for ever on a FIFO (score, recheck, derive, verify, log, attest-check, spread, log append, rerun) and read a file with no newlines whole (300 MB became 626 MB, so a symlink to /dev/zero would exhaust memory). All reads now go through one path: regular files only, opened non-blocking so a FIFO is refused rather than waited on, size-capped (1 MB seeds and key lists, 16 MB JSON, 32 MB ladders, 64 MB logs and answers) with the cap re-checked while reading in case the file grows, hashing streamed and regular-file-only. All 19 probe cases now refuse in about 0.1 s; a test covers a FIFO, a symlink to /dev/zero, a sparse 70 MB file and a directory across 13 invocations, and removing the regular-file check from either tool is caught (the size pre-check is deliberately redundant with the bounded read loop, so removing only it is not). Hashing a big regular file (log append --file) is intended and not capped. Also closed on the way: deeply nested JSON in an attestation file raised RecursionError (the file fuzz had never nested deeply there). A slip while probing: the first run used timeout, which does not exist on macOS, so every case "exited 127" and looked clean. It was caught because 0 tracebacks across 9 hanging tools was implausible.
  • Numeric command-line options are bounded and fuzzed (found by auditing the audit). The file fuzz corrupted files but never the options. Fuzzing 146 odd values (0, negative, NaN, inf, 1e400, 20-digit integers, text, empty) over every numeric option of both tools found 29 failures: --boot, --trials and -k at 0 or below crashed with IndexError/ZeroDivisionError/ValueError; derive --size -1 hung and --size 0 crashed inside the author's code; an invalid --fresh-seed crashed; huge --boot/--trials ran until killed; and score --boot 6000 wrote a result that recheck then refused (the two caps disagreed after one was tightened). All options now have ranges (--boot 1..5000, --trials 1..2000 with trials x boot <= 200,000, -k 1..1000, --repeat 1..50, --tolerance 0..1000, --min-gap 0..100, derive/verify sizes inside the challenge's declared range), violations are one-line usage errors, and the whole 146-case sweep now takes 13 s instead of timing out. A test runs it and another pins that the largest accepted --boot still rechecks; reverting each of five fixes in a copy is caught. Measured cost of the default sandbox: verify 57 ms unsandboxed, 130 ms sandboxed.
  • Re-audit of those fixes. The redesigned cross-seed check was measured for false failures over 6,000 (seed, size) cells on the toy domain (worst case 1 of 6 instances identical, limit is 3), 3,000 on dlog and 25 on aiinfer: none. The full export and fuzz suites passed six times concurrently under CPU load (no timing flakes). The docs' sandbox promises were each given a test that can fail: the five credential directories (~/.ssh, ~/.aws, ~/.gnupg, ~/.config/gcloud, Library/Keychains; removing any one from the deny list is caught), verify --selftest refusing where there is no sandbox, and export refusing a declaration that writes a cache file next to itself (it compiles and probes fine because the author's directory is writable; the sandboxed self-test is what stops it). A mistake in the write-up was caught too: it documented 40 mutations; there are 43.
  • Limits that bound the work a file can demand, and reproducibility. Scoring is linear in records x bootstrap resamples (measured: 50,000 records at 400 resamples took 48 s per pair; a one-million-line ladder ran for more than ten minutes), so a scored ladder may not exceed 20,000 lines and a result file may not request more than 5,000 resamples, which bounds the worst accepted case near two minutes (real ladders have about a thousand records and use 400 resamples). The first version of this cap, 50,000 records with 20,000 resamples, still allowed about 40 minutes: found by timing it. Exporting the same declaration twice produces byte-identical bundles (tested), so anyone can re-export and compare MANIFEST.sha256 with a published bundle's. Paths with spaces and non-ASCII characters work through score and recheck.
  • Every input is fuzzed. test_fuzz_bundle.py corrupts, at random, every input the tools read (ladders, result files, signed and unsigned attestations, checkpoints, measurement files, logs, answers, ladder records) and requires that nothing raises. The first run found 31 distinct crash classes (the worst: a validly signed attestation missing one field crashed attest-check, a denial of service a hostile signer could cause); further seeds found OverflowErrors in spread and recheck; all fixed. Twelve further seeds at 400 cases per surface ran clean. A result file may not request more than 20000 bootstrap resamples, must bind every ladder it names by hash, and files are written with exclusive-create so "never overwrites" has no race.
  • Statistical checks in the self-test have measured false-failure rates. The reuse check (another instance's witness accepted) failed ~5% of random-seed runs as single samples, then ~0.07% as a 25% rate over 30 pairs, because at tiny sizes instances share factors and hits cluster (distribution measured over 3000 seeds); they now fail above 50% and warn above 25%. A real lookup-table verifier (accepts any odd number) still fails; a test pins both directions, and a 400-seed test pins the false-failure rate at zero.
  • The power table's noise is measured, not just assumed. score.py reports each pair's observed within-bin noise (real dlog stride-4 vs reference: 0.19 bit, against the 0.6 assumed), says so when it is clearly higher than assumed, and re-simulates the certifiable range at the observed value; score.py power --pair-noise X --min-gap G re-simulates on demand from the compiled profile, and compare prints its own simulated power and its false-declaration rate at a true gap of 0. The simulation draws ladders from the compile-time profile (median per size, spread, cap), so it answers "what could this ladder resolve", not "what is this solver's real noise" (that is the measured number).
  • A solver beyond the ladder is told what it would take. When the faster solver costs under the 0.5 s floor on most instances the slower one finds hard, score and compare print the raw median gap as description (never a bound) and the cost the slower solver would need (about 0.5 s x 2^gap), and say plainly when that exceeds the cap so no ladder under this cap can resolve it (dlog's bsgs vs stride-4: about 11.5 bits needs about 1,463 s, cap 120 s).
