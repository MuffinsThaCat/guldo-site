Open to outside proposals

Propose a problem. If it holds up, it becomes a challenge anyone can verify.

You can say exactly when an answer is right, and you have a plain solver to compare against. Write those two things, and how to make test questions, and send them as one file. An operator reads and tests it before anything is run. If it holds up, it can be compiled into a fair test.

What it is not

Not an upload, and not a promise

A proposal is a public GitHub issue. Nothing runs when you send it, and sending it does not promise a round. The operator may decline, ask for a stronger baseline, or ask for another name, in their own time.

Status: new. The project has tested this path, including on Linux. No proposal from outside the project has been through it yet, so expect rough edges, and tell us when you find one.

How to prepare one

1

Install the tool

Download it from the Install page. The download there always includes the proposal commands.

pipx install ./guldo-0.1.4.zip
2

Write the three pieces

How to make a test question from a secret number, how to check an answer exactly, and a plain baseline solver. Keep your files in a folder of your own.

export SVP_DOMAINS_DIR=$HOME/my-domains
guldo compile init mything
guldo compile check mything

Pick a name that is not already on the Domains page. When check ends with “The declaration is VALID; it is just not compiled” and exits with status 1, that is the success message here: it is on purpose, and the operator does the compiling.

3

Screen and pack

The screen is the one the operator runs. Fix every FAIL line, then pack it into one file. Use your GitHub handle as the contact: the issue is public.

guldo intake screen $SVP_DOMAINS_DIR/mything
guldo intake pack $SVP_DOMAINS_DIR/mything --out mything.bundle.json --contact "your-github-handle"
4

Open an issue

Title it Proposal: mything and paste the whole file in a code block. If it is too long for an issue, attach it as a .txt file. One proposal per issue.

Open the issue

What happens to it

  • The operator runs the same screen again from scratch. Your own pass does not count.
  • It is run once in a limited process on the operator's machine, with a time limit and a memory limit, and the result is recorded.
  • The operator reads both files in full before anything is accepted. That reading is the real check: the screen is not a sandbox.
  • If accepted, the files go into the project's domains. That does not compile them and does not open a round: each is a separate, later decision.

What the screen allows

  • Plain Python that imports only: array, binascii, bisect, collections, decimal, fractions, functools, hashlib, heapq, hmac, itertools, math, random, statistics, struct.
  • Functions and constants only: no classes, no reading or writing files, no printing, and no running of text as code.
  • A REFERENCE_NOTE of at least 40 characters saying what the baseline is and what is known to beat it. A baseline nobody described is the main way a challenge becomes cheap.
  • A SPEEDUP line naming the kind of speedup it tests, one of lattice, number-theory, combinatorial, ai-inference, quantum, other. Related problems sit together (it is a filing label, not a ranking), and the queue and the Domains page are grouped by it. The line is advised, not required: without it the proposal is listed as unsorted.
  • Files up to 64 KiB each.

The screen tells you exactly what to change.

What you agree to

You keep the copyright in what you send. By opening the issue you confirm that you wrote the code or have the right to share it; that it is public the moment you post it (a rejected proposal stays public too: GitHub keeps an issue's edit history, and only the repository's owner can delete an issue, so ask the operator if something must come down); and that you give the Guldo project permission to use, run, modify and publish your declaration and reference as part of a challenge and its certificates, and to credit the GitHub handle you gave. If you want your files under a particular licence, say so in NOTES.md and the project will tell you if it cannot accept that.

What this cannot do

It cannot judge whether your problem is worth certifying, or whether your baseline is honest: the operator does that by reading. A challenge made from it measures speedups over your baseline only, and its certificates say which baseline that was. What a certificate does and does not prove is on the Limits page.
