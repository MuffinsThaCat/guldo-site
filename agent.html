Agents

Verifiable agent evaluation

The speedup-verification protocol (instances that are a pure function of a committed secret seed, exact verifiers, recomputable certificates) applied to AI agents: pre-registered plans, hash-chained trajectories, exact statistics, signed receipts and witnesses, and the code for a public log of certificates (none is running yet). Everything here is checkable by anyone with Python 3.9+ and a copy of the repository; only running a real model needs more (an API key and your own money).

Status, stated plainly

Real model runs: 5. Independent witnesses outside the project: 0. Official rounds (run on the separate verified evaluation machine): 0. Certificates in the public log: 0. Each recorded real-model run is a statement about that configuration, on those generators, sizes and caps, on its date, and about nothing else. Runs on a public practice seed certify nothing. Five recorded run sets. LOCAL qwen2.5:3b (via Ollama, one domain): two 16-instance rounds (one attested, but one person ran both proxy and operator) and a 4-trial practice run. A BLACK-BOX vendor-style agent on a joint seed: 9/16 vs 5/16, no difference shown, one person played every role. HOSTED claude-haiku-4-5 and claude-sonnet-5-5 on the PUBLIC practice seed (9 trials each, 4 attested): they show the method, not a certified number about either model. No hosted model has been judged on a secret seed. A biased first attempt is not counted. See agent_eval/real_runs_2026-11-27/.

The two models on the same 9 instances

claude-haiku-4-5 as the baseline, claude-sonnet-5-5 as the candidate. Solve rate: no difference in solve rate shown. Cost in proxy tokens: neither is shown cheaper. 9 instances cannot rank two models, and the rules refuse to claim more than the data support.

What the recording proxy did

4 trials went through a recording proxy (a separate process that forwards each request unchanged and signs a receipt for it): 24 signed exchanges, one per model call. The genuine ladder is ATTESTED. A hand-edited copy (one reply rewritten, and every token count and hash repaired so that it passes ordinary ladder verification) is rejected by the proxy log: research/1/0 trial 0 turn 0: no unused exchange in the proxy log matches this turn. That is the check that closes the gap in the limits above: a ladder that is internally flawless can still be invented, and only a record kept by someone else can show it.

What these runs do not show

  • Anything about a model on a hidden seed: every instance here can be derived by anyone.
  • Independence: the same person ran the proxy and the agent. This shows the mechanism works against the real provider, not that an independent verifier was involved. The guarantee needs a proxy and key outside the operator's control.
  • A ranking of the two models: 9 instances, domain research, sizes 1, 2, 3, one trial each.
  • Anything about answer quality beyond solve rate, other domains, or larger sizes.

Check it yourself

Download the files (every one is linked in the table above and listed in the folder's README; the proxy's signed log is here and the public key to pin is here). The signing key and the API key are not published. Then, with the tool installed:

guldo agent verify haiku45.jsonl --practice --plan plan.json
guldo agent check claim.json haiku45.jsonl sonnet55.jsonl
guldo agent-proxy verify ladder.jsonl proxy_log.jsonl --trusted verifier.pub --practice

The hand-edited ladder is published only as a labelled negative control, in a folder named NOT_A_RESULT: it is not a result and must not be indexed or cited as one. Run the third command on it with the same proxy log to see it rejected.

What a certificate does not show

  • A verified result shows that its records are consistent and correct, NOT that a particular model produced them (receipts from a proxy the verifier controls, or independent witnesses, narrow this to trust in a key).
  • Tokens are proxy tokens (ceil of UTF-8 bytes / 4 of the exact context sent each turn plus the output) unless a ladder was attested with the provider's own usage figures.
  • The task generators are public: committing to a secret seed hides the judged instances, and a SEALED domain also hides its names, wording and ranges, but neither hides the skill being tested.
  • Domains that run agent-written code (coding, bugfix) execute it on the verifier's machine with resource limits, which is not a sandbox: use a throwaway VM or container.
