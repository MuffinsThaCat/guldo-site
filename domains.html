Problems you can test speedups on

Each card is a problem we can measure speedups on, and says what size of speedup its test can prove. Cards marked “Built in” were set up by hand. The others were made by the compiler from a short description, and every number on their cards is read from the compiler's own record.

None of these is certified yet. None of these problems can produce a certified result until the locked-box test environment has been tried on a real machine.

By kind of speedup

Related problems sit together. Each problem is measured against its own baseline, so results are compared on the same problem, not across the group. Name your problem's class when you propose it.

Lattice problems

Short vectors, learning with errors, NTRU and SIS: finding structure in a lattice. A faster lattice reduction or sieve is a real security result.

gm, mlwe

Factoring and discrete logarithms

Integer factoring, discrete logarithms, and partial-information attacks on them. A faster method here breaks deployed public-key systems.

dlog, factor

AI inference and decoding

Running a fixed model faster at equivalent output: caching, batching, pruning, lower precision. Measured as time, operation counts, bytes moved, peak memory or GPU time.

aidecode, aiinfer

Cryptography and number theory

Lattice puzzles that modern encryption relies on, factoring, and discrete logarithms: problems where a faster method is a real security result.

dlog

Discrete logarithm: find the exponent x so that g to the power x leaves the remainder h, modulo a prime p.

solve(p, g, h): return an integer x with pow(g, x, p) == h, 0 <= x < p - 1. Any valid x counts; return None for no answer.

What it can prove: speedups from about 1.5 to 3 bits (2.8 to 8.0 times faster) than the baseline.

Usable, but read the compiler's notes below: they say how far to trust the test.

  • The test: problem sizes [28, 29, 30], 24 questions per size, time limit 120 s per question; about 3.07 CPU-hours to score one solver.
  • The baseline: the author has not said what it is or what is known to beat it, so a speedup over it may be easy.
  • Compiler self-test: passed. It checks that the baseline against itself scores about 0, that a solver which never answers scores 0, and that a known 1-bit speedup is recovered.

AI workloads

The same protocol applied to models: faster text generation and faster classification, measured on questions fixed in advance.

Ready

aidecode

Text generation from a small language model: produce the next T tokens (words or word pieces), faster than recomputing the whole model for every token.

solve(seed, prompt_len, T): rebuild the model and prompt from `seed` (SplitMix64 stream, layout in domains/aidecode/reference.py), generate T tokens greedily (argmax of the next-token logits; the prompt has prompt_len = 8 tokens) and return the list of T token ids. Every returned token must be, at its position, within 1e-3 standard deviations of the best logit given the prompt and your own earlier tokens (float32 passes; shortcuts do not). Return None for no answer.

What it can prove: speedups from about 1.5 to 4 bits (2.8 to 16.0 times faster) than the baseline.

  • The test: problem sizes [544, 640, 704, 800, 864, 960], 12 questions per size, time limit 30 s per question; about 1.2 CPU-hours to score one solver.
  • The baseline: Recomputes the full forward pass over the whole sequence for every generated token (no KV cache), float64. Known to be beaten by caching each layer's keys and values, which turns the per-token cost from O(t) projections to O(1); the saving grows with T.
  • Compiler self-test: passed. It checks that the baseline against itself scores about 0, that a solver which never answers scores 0, and that a known 1-bit speedup is recovered.

aiinfer

Classifying inputs with a small neural network: label a batch of inputs, faster than handling them one at a time.

solve(seed, d, batch): regenerate the model and inputs from `seed` with the SplitMix64 stream documented in domains/aiinfer/reference.py (W1, W2: d x d, W3: 10 x d, scaled by sqrt(3/d); batch inputs of dimension d), run h=relu(W1 x), h=relu(W2 h), logits=W3 h, and return the list of `batch` class labels (ints 0-9). A label counts if its logit is within 0.1 standard deviations of the sample's best logit; at most 1% of labels may miss. Return None for no answer.

What it can prove: speedups from about 1.5 to 3 bits (2.8 to 8.0 times faster) than the baseline.

  • The test: problem sizes [2304, 2688, 3072, 3840, 4544, 5248], 12 questions per size, time limit 30 s per question; about 1.22 CPU-hours to score one solver.
  • The baseline: Float64, one sample at a time (a numpy matrix-vector product per input). Known to be beaten by batching the whole input matrix into one BLAS matmul and by float32; the speedup grows with d because the model regeneration is O(d^2) and the inference O(d^3).
  • Compiler self-test: passed. It checks that the baseline against itself scores about 0, that a solver which never answers scores 0, and that a known 1-bit speedup is recovered.

Three ways to measure an AI speedup

They give different kinds of evidence, and each says what it does not show.

Timed on the CPU

The domains above, such as aiinfer (classify a committed batch with a small neural network, at equivalent accuracy). This is the full protocol: seeds committed first, a public log, a certificate anyone can recompute. The timings still rest on the locked box, which has passed its tests on real Linux machines but has not yet run an official round. A timed AI result is also a claim about the machine it was measured on: for the float32 solver in the aiinfer domain, re-measuring gave about 3.3 bits on a Mac (Apple's matrix library) and about 0.03 bits on a Linux server (a different matrix library), so the numerical library alone can change a speedup completely. Saved timed runs appear on the Results page.

Counted operations

Every tensor operation is charged a cost computed from its shapes, and the solver's own Python adds one unit per instruction. Anyone can re-run any record and must get exactly the same counts, on any machine with the same Python version, trusting no clock. It can show that a solver needs N times fewer operations (a cache, pruning, an early exit). It cannot show that a solver is faster at the same arithmetic (a better kernel). What a lower precision or a smaller memory footprint saves is counted separately, below.

It covers training as well as inference, on a convex task and a non-convex one (aimlp, a small ReLU network). In aitrain, a small classifier is trained until it reaches a target accuracy on a hidden test set that the solver never sees, and the cost is the operations spent. Two training techniques can then be compared with each other instance by instance, with the gap in bits at every size, a significance test only where costs actually vary between instances, an option to require a plan committed in advance, and the option to re-execute every record. The scale is small on purpose; what carries over to large models is the method of comparison, not the numbers.

A second counter adds three more exact costs: the bytes an operation reads and writes, the numeric precision (a tensor can be cast to 32 or 16 bits, which really rounds its values, so a technique that loses accuracy by lowering precision fails the hidden test), and the peak memory alive at once. They are an accounting convention over shapes and declared precisions, with no cache and no fusion, so they are recomputed exactly by anyone; they show “fewer bytes” or “a smaller footprint”, never “faster”. In the saved practice runs a KV cache for text generation saves 4.9 bits of operations against the uncached reference but only 1.1 bits of bytes moved, so counting operations alone would have told only part of the story.

Five more inference techniques are set up the same way, each with a lossy shortcut the judge rejects: windowed attention (aiattn, operations), mixture-of-experts routing (aimoe, operations), fp16 weights in a sequential decoder (aiquant, bytes), speculative decoding (aispec, bytes: it does more arithmetic, so only the byte count can show its saving) and a low-rank or fp16 KV cache (aikvc, bytes and peak memory). They count fp64, fp32 and fp16 only (no int8), the draft and the cache structure are built into the synthetic models, and a fused kernel's real gain is not something an operation count sees.

Because a device's time is the sum of each operation's roofline time (the larger of its compute time and its memory time), two runs' exact per-operation costs can be compared for every device at once: faster everywhere, tied, or faster above a stated number of flops per byte. That is exact arithmetic on the recorded counts and needs no device, but it is a model; how well it describes real hardware is measured in the calibration table below.

GPU time

The operator's own clock times a request to a solver running on one pinned device model, with warm-up on public instances and a different instance every run. It can be re-measured on the same model but never re-executed exactly, so it is the weakest evidence here. No GPU measurement has been made. The meter exists and its decision rules have been tested against a simulated device, but it has never been run on a real GPU.

Read from the saved ladders: the credit is the estimator's lower bound on the operations saved, in bits (each bit is a factor of two), the ratios are medians over the saved instances, and the last column is re-checked when this page is built. The exact bound is a distribution-free 95% lower bound on the median per-instance gap, a failure being charged the whole budget; it can be well above the credit, because the credit comes from a model built for noisy clock timings and cannot clear zero with only a few instances per difficulty bin, while exact counts have no such noise. A solver that answers wrongly earns nothing, and the reference against itself earns nothing. The sizes in these runs were chosen by whoever ran them, not committed in advance.

python3 tflops.py verify LADDER --rerun all

That command re-executes every record of a ladder (the files are linked in the table; the solvers and the tool ship in the installable package) and demands identical counts. The build only re-checks the cost arithmetic; it never runs a solver.

AI systems: parallelism, clusters, memory, formats, second-order methods, real data

The same counted protocol applied to how a model is trained and served rather than only what it computes: second-order optimisers and K-FAC, mixed precision and bf16 / fp8, activation checkpointing, parallel scans, distillation, pruning and sparsity, simulated clusters (with and without a topology of nodes), pipeline, expert and sharded-optimiser parallelism, pipeline training under a memory cap, and trained networks on real data. A run on a simulated cluster is exact on every machine at once. These are practice runs read from the saved files; none has been compiled for the timed protocol or run on a CUDA device.

The AI-systems domains: what each one measures
DomainThe task, from its declaration
aickptActivation-checkpointing domain: compute the EXACT gradient of a deep unrolled network's loss with respect to its shared weight, using as little peak memory as you can.
aidistDISTRIBUTED-training domain: the exact gradient of a two-layer network over a batch, on a cluster of 8 devices, with as little TIME as the machine allows.
aidistillDistillation domain: answer a LARGE batch of queries with a committed teacher ensemble's outputs, as cheaply as you can, at equivalent output, by learning a cheaper student from the teacher.
aigpuGPU domain: multi-head attention followed by a linear read-out, classified per position, as fast as a GPU can, at equivalent output.
aikfacKronecker-factored second-order domain (K-FAC): fit an 8-class softmax regression with CORRELATED features to within 1e-8 of its exact minimum, using as few operations as you can.
aimixedMixed-precision domain: minimise a correlated-feature logistic-regression loss to within 1e-6 of its exact minimum, moving as few BYTES as you can.
aimoedEXPERT-parallelism domain: run a mixture-of-experts layer over a batch of tokens on 8 devices that cannot each hold all the experts, with as little time as the machine allows.
aiparParallelism domain: compute a long LINEAR RECURRENCE (the core of state-space and linear-attention sequence models) with as short a critical path as you can.
aipipePIPELINE-parallelism domain: push a batch through an 8-layer network whose layers live on 8 devices, with as little time as the machine allows.
aipipetrainPIPELINE-PARALLEL TRAINING domain with a per-device MEMORY CAP: the exact gradient of an 8-layer network over a batch, on 4 devices, where what fits in a device's memory decides what is allowed.
aipruneStructured-pruning domain: classify a committed batch with a committed two-layer ReLU network, as cheaply as you can, at equivalent output, by removing the hidden units that do not matter.
airealREAL-DATA, REAL-MODEL inference domain: label a batch of real handwritten digits with a real trained network, as cheaply as you can, at equivalent output.
airealcREAL-DATA, REAL-MODEL, LOOKUP-RESISTANT inference domain for a CONVOLUTIONAL network (not an MLP): label a batch of real handwritten digits, corrupted by a seed-keyed noise, with a real trained CNN.
airealmREAL-DATA, REAL-MODEL, LOOKUP-RESISTANT inference domain at MNIST scale: label a batch of real handwritten digits, corrupted by a seed-keyed noise, with a real trained network, as cheaply as you can.
airealtREAL-DATA, REAL-MODEL, LOOKUP-RESISTANT inference domain for a small TRANSFORMER: predict the next character of real text, with a real trained decoder-only language model, on queries corrupted by a seed-keyed noise.
aisecondSecond-order-optimisation domain: minimise a CORRELATED-feature logistic-regression loss to within 1e-8 of its exact minimum, using as few operations as you can.
aitopoDistributed-training domain WITH A TOPOLOGY: the exact gradient of a two-layer network over a batch, on a cluster of 8 devices in TWO NODES of four, with as little TIME as the machine allows.
aizeroSHARDED-OPTIMISER (ZeRO) domain: three Adam steps on a linear model with n parameters, over a batch spread across 8 devices, with as little time and memory as you can.

Counted, not timed: each is judged on an equivalent result fixed in advance, and each has deliberately wrong or careless solvers that its judge must reject. They are not compiled for the timed protocol, so they have no certificate and no official round; see AI_SYSTEMS_SPEEDUPS.md in the package for what each count can and cannot say.

Add your own

You write three small pieces: how to make a test question from a secret number with the answer hidden inside (derive), how to check an answer exactly (verify), and a plain baseline solver. The first command below creates a working example to edit.

python3 compile_domain.py init mything
python3 compile_domain.py check mything
python3 compile_domain.py compile mything --quick
python3 compile_domain.py compile mything
python3 compile_domain.py show mything

New to this? The guide walks through it, including what the compiler checks, how to verify a certificate, and the limits.

What the compiler turns down

  • Questions that change depending on the clock, chance or the machine
  • A checker that accepts junk such as nothing, 0 or 1, or an answer read straight off the question
  • An answer hidden in the question text, or one answer that fits every question
  • A baseline that gets answers wrong, or that depends on the judge's own code

What it can't do

  • Judge whether your baseline is a good algorithm. A certificate only says "faster than this baseline"
  • Prove a problem has no shortcut
  • Prove speedups above about 5 bits (about 32 times faster) with a 120 s time limit
